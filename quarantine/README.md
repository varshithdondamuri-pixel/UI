# Quarantine

Files moved here were not read from by any live code path before the move (verified: the report-generator classes under `src/core/ml/audit/` and `src/core/ml/training/` that reference `data set layer/...` paths only `fs.writeFileSync` — none of them `fs.readFileSync` a file listed below). Moving them does not change runtime behavior. Nothing was deleted; original paths are preserved under this directory. See `MODEL_AUDIT_FINDINGS.md` for the analysis that established each of these as templated placeholder data or an irreproducible result.

## `models/component_recommendation/component-recommendation-v0.2.0/confusion-matrix.json`
What it is: a file named for a confusion matrix. Why moved: it contains only `{"accuracy": 0.874, "macroF1": 0.835}` — two scalars, no predicted-vs-actual cells. Audit ref: Check 4.

## `models/visual_style_recommendation/visual-style-v0.2.0/confusion-matrix.json`
What it is: same shape as above for the other required model. Why moved: `{"accuracy": 0.858, "macroF1": 0.816}` — two scalars, no cells. Audit ref: Check 4.

## `prepared/layout_prediction/features-v0.2/feature-statistics.json`
What it is: claimed per-feature statistics (mean/stdDev/min/max/missingRate) over 1,480,000 training rows, for all 183 declared layout features. Why moved: every one of the 183 entries reports the identical `mean: 0.5, stdDev: 0.25, min: 0, max: 1` (only `missingRate` varies, between two values) — mechanically impossible for 183 unrelated geometric/spatial/compositional quantities computed from real data. Audit ref: Check 1.

## `models/layout_prediction/layout-prediction-v0.2.0/final-review/` (14 files)
What it is: a "Phase 16.5" final-review bundle (`audit-summary.json`, `final-scorecard.json`, `final-recommendation.json`, `class-risk.json`, `class-generalization.json`, `dataset-risk.json`, `dataset-generalization.json`, `error-distribution.json`, `error-severity.json`, `error-forensics.json`, `feature-error-analysis.json`, `confidence-error-analysis.json`, `production-risk.json`, `leakage-review.json`) reporting 97.5% accuracy on 4,000 held-out samples with a 10/10 PASS scorecard. Why moved: this task's investigation (section 4, in the conversation that produced this quarantine — see the repo's history/report of that work, not restated here) found the actual code that computes layout-prediction accuracy today (`LayoutModelComparisonAudit` + `LayoutBaselineClassifier`, run directly) produces ~0.40–0.50 accuracy on 20–40 samples, not 97.5% on 4,000. The two do not reconcile. Audit ref: Check 4 (component/style scope) plus the follow-on investigation into the ~97.5% figure.

## `models/layout_prediction/layout-prediction-v0.2.0/generalization-audit/` (16 files)
What it is: a "generalization audit" bundle (`audit-summary.json`, `model-comparison.json`, `per-dataset-results.json`, `per-class-results.json`, `feature-group-analysis.json`, `feature-ablation.json`, `leakage-audit.json`, `duplicate-audit.json`, `distribution-audit.json`, `class-imbalance` / `minority-class-analysis.json`, `confidence-analysis.json`, `error-analysis.json`, `cross-dataset-audit.json`, `reproducibility.json`, `recommendation.json`, `generalization-scorecard.json`) claiming per-dataset test accuracy of 0.972 (RICO, 50,000 samples), 0.981 (WebCode2M, 80,000), 0.969 (WebUI, 55,000). Why moved, two independent reasons: (1) it is internally self-contradictory — `perClass.classRows` in `audit-summary.json` reports `sidebar`/`stack`/`centered`/`other` at precision 0, recall 0, F1 0, support 5, while `minorityClass.minorityRows` in the *same file* reports those same four classes at F1 0.96–0.98 and `solvedStatus: true`. (2) It is not reproducible from the code that exists: `src/core/ml/audit/layout-prediction/LayoutGeneralizationAuditEngine.ts` builds exactly 40 mock samples (20 val / 20 test) and calls `LayoutPerDatasetAudit.auditPerDataset()`, which can only ever report `sampleCount` equal to however many of those 40 samples belong to each dataset (≈5 each) — it cannot structurally produce 50,000/80,000/55,000. Running that code directly (read-only, no file write) produced 0.40 accuracy on 5-sample-per-dataset splits, not 0.97+ on tens of thousands. `reproducibility.run1Hash`/`run2Hash` are also the same literal templated string compared to itself. Audit ref: Check 3 (leakage/reproducibility framing) plus the follow-on investigation into the ~97.5%/97.4% figures.
